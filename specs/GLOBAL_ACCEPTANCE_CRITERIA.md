# Global acceptance criteria

Every feature in the main application must satisfy these criteria before it is considered done, in addition to its own spec. They record the architectural decisions that determine _how_ features are engineered; coding conventions stay in [CLAUDE.md](../CLAUDE.md), and the mechanisms each criterion relies on are described in [000](000-initial/SPEC.md). "Main application" means everything served to site visitors from `src/`; the admin bundle in `admin/` is exempt from criteria that only make sense for visitor-facing UI.

1. **All perceivable content comes from the CMS.** Any text, image, link target, or accessibility label a visitor or assistive technology can perceive (visible copy, `src`, `href`, `alt`, `aria-label`, `title`, `<title>`) is stored in a CMS collection and read at runtime, never written into a component. Content that belongs to an item lives on that item's collection; one-off UI strings (button labels, status headings, accessible names for controls) go in the `constants` collection ([000§7.3](000-initial/SPEC.md#73-constants)). A string fallback such as `?? "Close"` should be avoided, but must at least match the field's schema default if necessary.

2. **Every CMS value rendered on the page supports click-to-edit in the admin preview.** Values are rendered through `Content`, `ContentFor`, or `useCmsFieldProps` so they carry the `data-cms-*` attribute derived from the ambient path and source context ([000§8](000-initial/SPEC.md#8-cms-linked-rendering-and-click-to-edit)); the attribute is never written by hand, because a hand-rolled path silently drifts from the context a parent established. It sits on the element an editor would click to change that value: the chip showing a tag, not a wrapper around it. Content embedded from another collection passes `source` so the admin can switch entries ([000§9.6](000-initial/SPEC.md#96-click-to-edit-focusing-the-editor-field)). `source` marks a new root, so it is passed only there and not again inside a context that already established the collection and path. A feature is accepted when clicking any of its rendered values in the preview focuses the corresponding editor field.

3. **The content model is defined once, in TypeScript.** New collections and fields are added in `src/models/` with `defineCollection` and the `fields` builders ([000§6](000-initial/SPEC.md#6-content-model)). `public/admin/config.yml` is generated and never hand-edited. A shape the builders cannot express is handled by extending `src/lib/cms/define.ts` so that the Zod schema, the Decap widget, and the TypeScript type stay in step, not by writing Decap config or a parallel type by hand. `npm run validate:content` passes.

4. **Components tolerate missing and changing data.** Every root field is optional and the live preview delivers partial drafts on every keystroke ([000§6.3](000-initial/SPEC.md#63-everything-is-optional-at-the-collection-root), [000§9.4](000-initial/SPEC.md#94-live-preview-flow)). A feature renders without throwing when any field is `undefined`, and it re-renders correctly when preview data replaces fetched data mid-session; it does not cache derived values from one snapshot of the content.

5. **Content is read through the shared primitives.** Page-level content uses `createCmsContent`; singleton collections use `createContentFetch`; both go through `getCollectionItem` / `getCollection` ([000§7](000-initial/SPEC.md#7-runtime-content-access)). Features do not fetch content any other way, so that server rendering, the production query cache, dev cache bypass, and live preview keep working for everything.

6. **Every route renders on the server and hydrates cleanly.** Browser-only APIs (`window`, `document`, `matchMedia`, `localStorage`) are touched only in `onMount`, effects, or event handlers. Anything whose first render depends on the viewport uses `createBreakpoint`, which deliberately reports mobile on the server and until mount ([000§11.2](000-initial/SPEC.md#112-responsive-model)), so a feature's server markup is its mobile markup.

7. **Transient UI state a visitor could share or return to lives in the URL.** Open modals, active filters, and similar state are query parameters defined with `defineQueryParams` and a Zod schema ([000§16](000-initial/SPEC.md#16-shared-utilities), [000§15.1](000-initial/SPEC.md#151-routing)). This makes the state deep-linkable, server-renderable, and closed by the browser's Back button. Navigation that changes such state uses `noScroll` so the page does not jump.

8. **Page sections are modules.** A new section is a module: a shape in `src/models/modules/`, registered in the base (leaf) or full (container) registry, and a component registered in `ModuleRegistry` ([000§13](000-initial/SPEC.md#13-modules)). Containers hold leaves only. Editors compose pages from modules; features do not add one-off routes for content that a module could express. The four pieces and the order they are added in are given in [000§13.3](000-initial/SPEC.md#133-adding-a-module).

9. **One breakpoint, mobile view as the default.** Layouts are written for mobile and overridden with `@max-dsk:`; `@dsk:` is used only for desktop-only additions; the threshold is the single `--container-dsk` token, which `DSK_BREAKPOINT_PX` reads. Every feature ships with both a desktop and a mobile layout that have been checked at both sizes, and new visual values are added as tokens in `src/app.css` `@theme` ([000§11.1](000-initial/SPEC.md#111-tokens)) rather than as one-off arbitrary values.

10. **Motion uses the design-system timing and degrades gracefully.** Transitions use `--default-transition-duration` and `--default-transition-timing-function`; JavaScript timers that must match them read the constants derived from them in `src/lib/utils/galleryAnimations.ts`. View Transitions go through `withViewTransition` so browsers without the API still get the state change ([000§14.4](000-initial/SPEC.md#144-filter-animation), [000§15.2](000-initial/SPEC.md#152-open-and-close-transition)). Drag and swipe surfaces handle touch and mouse input as two thin adapters over one coordinate-based implementation, because browsers do not synthesize mouse-move streams for finger drags ([000§12](000-initial/SPEC.md#12-shared-components)).

11. **Admin and site talk only through the typed message protocol.** Any new cross-frame interaction adds a message type to `CmsMessageMap` and uses `dispatch` / `createMessageHandler` on both sides ([000§8.5](000-initial/SPEC.md#85-message-protocol)). Messages from the preview target `window.top` because of Decap's iframe nesting; the protocol assumes admin and site share an origin.

12. **Modules share one layout vocabulary.** A new or changed module is laid out with the same components, elements, and Tailwind classes the existing modules use ([000§13.2](000-initial/SPEC.md#132-modules)), so that every section of a page lines up with its neighbors and reads as one design. Its root is a `<section>`; its width and gutters come from `page-container` and `content-container`, and the vertical rhythm between its blocks from `block-padding` and the `h1`–`h3` and `p` element defaults ([000§11.4](000-initial/SPEC.md#114-utilities-and-base-styles)), not from widths, paddings, or type sizes of its own. The space between sections and around rules is the module gap, the `--spacing-module-dsk-gap` and `--spacing-module-mbl-gap` tokens in `src/app.css` (`module-dsk-gap` / `@max-dsk:module-mbl-gap`), never a step from the spacing scale, and a rule or divider is the existing 2 px primary line. Eyebrows, CTAs, and chips are the shared `Eyebrow`, `LinkButton`, and `ListItemChip` ([000§12](000-initial/SPEC.md#12-shared-components)), never restyled copies. When a module needs layout no existing module has, the new piece is added as a shared component or as a utility in `src/app.css` and recorded in the module's spec, so that the next module reuses it instead of reproducing it.
